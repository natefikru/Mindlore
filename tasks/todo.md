# Mindlore: AI providers, voice and photo transcription, titles, insights, entry dates

Branch: `feature/ai-providers` from `main` (after PR #1). The v1 capture-and-storage plan, its key decisions, and its review log are archived in `tasks/archive/v1-capture-storage.md`; its decisions about saving, recording, and transcription still hold.

Status: revision 5. Revision 3 folded in the first sub-agent plan review; revision 4 added photo entries and entry dates at the owner's request; revision 5 folds in the second review, of revision 4 (see "Review log"). Awaiting owner approval. Nothing below is implemented yet.

## Goal

Let the user bring an OpenAI API key and have AI work alongside their journal:

1. Speech to text through OpenAI, used instead of Apple's on-device recognizer when AI is on, with Apple as the fallback.
2. Photo entries: photograph journal pages in the app (or import them from the photo library), confirm the page order, transcribe the handwriting with an OpenAI vision model, review and correct the text, approve it.
3. Titles generated by Apple's on-device model (no key, offline) or OpenAI, or typed by the user. An entry with no title shows its first words.
4. Insights per entry (summary, moods, themes, tags, people and other proper nouns, open threads, custom prompts) shown in their own view, plus cleaned-up text for voice entries.
5. A "Run AI" action on any entry, for errors, entries that never had insights, and replacing old ones.
6. An entry date the user can change to the day the entry was actually written, separate from when it was added to the app, with a suggested date when AI finds one.
7. Settings that decide which of these happen.

OpenAI is the only provider this PR ships, because one key covers text, audio, and images. The code is shaped so Anthropic, Gemini, Groq, Deepgram, local servers, and the rest can be added later without touching the pipeline.

## Owner decisions (2026-09-15)

- OpenAI only for the prototype; build the abstraction so every other provider can be added.
- Apple Foundation Models is an option for title generation. On phones without it, the default is no AI titles: the user types one, or the entry shows its first words.
- When AI is on, cloud speech-to-text is the default over Apple's recognizer. Configurable.
- Insights live in a separate view from the entry text.
- The title is a field on `Entry`, editable by the user. AI fills it only while it is empty or still AI-written.
- Built-in insights: summary, moods, themes, tags, mentions (people, places, and other proper nouns), open threads, plus user-written custom prompts. Each can be switched off.
- Moods come from a larger vocabulary grouped into categories, each mood with a short description. Claude wrote the vocabulary at the owner's request.
- AI runs automatically at most once per entry. "Run AI" on a single entry covers everything after that: retries, missing insights, replacing insights, and older entries.
- **Cleaned-up text applies to voice entries only.** Voice is the one way in where no person reads the raw text before insights run. Typed text is the user's own writing, and photo transcriptions are reviewed and approved by the user. For voice entries, a setting applies cleanup automatically; otherwise it is a suggestion with one tap to apply. The original is never deleted and the user can always revert.
- **Photo entries** are captured in the app (document camera) or imported from the photo library. The user confirms the page order before transcription starts. Once transcription starts the order is locked; changing pages afterwards (reorder, add, delete) restarts the entry, after a warning that its text, title, and insights will be erased.
- **Photo transcriptions are reviewed before AI insights.** The user reads the text next to the page images, corrects it, and approves it. No title or insights run on a photo entry until the text is approved.
- **No offline fallback for photos.** On-device text recognition is too inaccurate on handwriting to be worth it. Photo entries wait for AI; the user can always type the text themselves.
- **Entry dates.** By default an entry's date is its full `createdAt`, date and time. The user can change it on any entry (typed, voice, photo) to a different day; a changed date is day-precision, because time doesn't matter for a backdated entry.
- **Suggested dates.** When AI can identify the date an entry was written (a date at the top of a journal page, a dated pasted entry), it is offered as a suggestion the user confirms.
- No privacy marketing claims in this PR. Existing copy that claims data stays on the device is replaced with neutral wording now; privacy wording gets its own review later. Engineering rules that protect data (keys in Keychain, no entry text or keys in logs) still apply.
- Scribe (obsidian-scribe) is inspiration, not a template. Borrowed ideas: separate transcription and text protocols, an OpenAI-compatible client parameterized by base URL, a schema built at runtime from the enabled sections, optional sections that return null. Deliberately different: keys in Keychain instead of plaintext, AI output kept out of the entry text unless the user opts in, a persisted queue with bounded retries instead of fire-and-forget, silence-aware chunking instead of cutting at arbitrary samples, extracted tags and mentions that feed a future knowledge graph, handwritten pages with human review.

## Research summary

Full reports were gathered by sub-agents on 2026-09-15. The parts that shaped the plan:

- **OpenAI speech:** `POST /v1/audio/transcriptions`, multipart, Bearer auth. Default model `gpt-transcribe` ($0.27/hr); `gpt-4o-mini-transcribe` is cheaper, `whisper-1` is the only one with word timestamps. 25 MB per file and, in practice, about 1400 s (~23 min) per request even though the docs only state size. Accepts flac, mp3, mp4, mpeg, mpga, m4a, ogg, wav, webm; **not CAF**. Our stored AAC is ~21 MB/hr, so duration is the binding limit, not size.
- **OpenAI text:** target Chat Completions (`POST /v1/chat/completions`), not the Responses API, because every OpenAI-compatible provider speaks Chat Completions and it does not store requests by default. Structured output via `response_format: {type: "json_schema", json_schema: {name, strict: true, schema}}`. Strict mode needs `additionalProperties: false` on every object and every property in `required`; optional fields are typed `["string", "null"]`, and a nullable enum must also list `null` among its enum values. JSON mode (`json_object`) requires the word "JSON" somewhere in the messages. A non-streaming response sends no bytes until it is done, so long outputs need a long request timeout. `finish_reason: "length"` means truncated output. `GET /v1/models` lists models (no capability metadata) and doubles as a key check. Current models: `gpt-5.6-luna` (cheap), `gpt-5.6-terra`, `gpt-6-astra`. Confirm IDs against `/models` when implementing.
- **OpenAI images:** Chat Completions accepts images as `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,...", "detail": "high"}}` content parts alongside text, with the same structured output. Handwriting accuracy depends on the model; the page model is a separate setting defaulting to the stronger `gpt-5.6-terra`. Confirm image input support and model ID in the live test. (Verify current image size and token accounting against the docs when Phase 3 lands.)
- **Handwriting OCR:** the build plan's research found Apple Vision at 72% versus Google Cloud Vision at 91% on handwritten receipts, and that multimodal LLMs correct errors using sentence context, which suits prose. Supports the owner's call to skip an on-device fallback.
- **Same shape elsewhere:** Groq, Mistral, xAI, DeepSeek, OpenRouter, Ollama, LM Studio, and self-hosted Whisper servers all accept the Chat Completions and/or `/audio/transcriptions` shape with a different base URL. Anthropic and Gemini need native clients later. Deepgram, ElevenLabs, AssemblyAI, and xAI speech each need their own adapter later.
- **Apple Foundation Models:** on-device, no key, iOS 26+. Requires an Apple Intelligence capable device with Apple Intelligence on; check `SystemLanguageModel.default.availability` (unavailable reasons include device not eligible, Apple Intelligence off, model not ready). About 4,096 tokens per session including output, so long entries are truncated before asking for a title. `@Generable` guided generation guarantees the output shape.
- **Capture APIs:** VisionKit `VNDocumentCameraViewController` captures multiple pages in order with edge detection, crop, and perspective correction; needs `NSCameraUsageDescription`. SwiftUI `PhotosPicker` imports from the library without a photo library permission prompt (it runs out of process), with multi-selection returned in selection order.

## Key decisions

### Providers and requests

**Three capabilities, one account.** A provider account (kind, base URL, display name, Keychain reference) can serve text generation, speech to text, page transcription, or all three. Settings pick an account and model per capability. For now there is exactly one account kind, `openAICompatible`, with an OpenAI preset. Adding a provider later means a new kind plus clients that conform to the capability protocols; the coordinators, settings shape, and views stay the same.

**Protocols per capability, not per vendor.** `TextGenerator` (`generate(TextRequest) async throws -> TextResult`), the existing `Transcriber`, and `PageTranscriber` (`transcribe(PageRequest) async throws -> PageResult`). `OpenAICompatibleTextGenerator`, `OpenAICompatibleTranscriber`, `OpenAICompatiblePageTranscriber`, and `FoundationModelsTextGenerator` conform. Text requests carry an optional image list, so the page transcriber is a thin layer over the text generator. Requests carry a portable JSON schema kept to the subset every provider accepts (objects, strings, numbers, booleans, arrays, string enums; no min/max, pattern, or recursion). If the server rejects the strict schema specifically (OpenAI's error names `response_format` as the parameter), the request is retried once in JSON mode with the schema and the word "JSON" in the system prompt; any other 400 is not retried. One tolerant parse path (strip code fences, take the first balanced object, drop unknown enum values) handles every response. `finish_reason: "length"` becomes `AIError.outputTruncated`, which is not retryable.

**Keys live in Keychain, config lives in settings.** API keys are `kSecClassGenericPassword` items under service `com.natefikru.mindlore.ai` (injected, so hosted tests use their own service name), account = the provider account's UUID, accessible `AfterFirstUnlockThisDeviceOnly`. Keychain is read on the main actor when a job starts and the key is passed into the request as a plain value. Non-secret account config is Codable JSON in `SettingsStore`. Keys never touch SwiftData, `UserDefaults`, logs, or diagnostics.

**Network, parsing, and image work stay off the main actor.** New value types (`ProviderAccount`, `AIError`, `TextRequest`, `TextResult`, `PageRequest`, `PageResult`, `JSONSchema`, `Mention`, `CustomInsightResult`) are declared `nonisolated` like `TranscriptionError`, so their `Codable` conformances work in `@concurrent` code. `HTTPClient`, the multipart builder, `StructuredOutputParser`, `AudioChunker`, and `PageImageProcessor` are `nonisolated`; request building, base64 encoding, JSON decoding, image resizing, and audio export never run on the main thread. Coordinators stay on the main actor and hold `PersistentIdentifier`s across awaits.

**Timeouts match the work.** `URLSession` ephemeral configuration, no URL cache. Model list and key test: 30 s. Text generation and page transcription: 300 s. Audio upload: 600 s per chunk.

**Provider errors carry codes, not bodies.** `AIError` maps HTTP status plus OpenAI's `error.code`/`error.param` into: `missingKey`, `invalidKey` (401), `permissionDenied` (403), `rateLimited(retryAfter:)`, `quotaExceeded` (429 `insufficient_quota`), `requestTooLarge` (413 or file-size errors), `contextTooLong`, `badRequest(code:)`, `serverError(status:)`, `offline(URLError.Code)`, `network(URLError.Code)`, `outputTruncated`, `invalidResponse`, `cancelled`. `offline` means nothing reached the server: the `URLError` code is one of `notConnectedToInternet`, `cannotFindHost`, `cannotConnectToHost`, `dnsLookupFailed`, `internationalRoamingOff`, `dataNotAllowed` **and** the task sent zero bytes (`countOfBytesSent == 0`, read from the task captured through the per-task delegate's `didCreateTask`). A matching code after bytes went out (the network dropped mid-upload) is `network`, as are `timedOut` and `networkConnectionLost`, where the server may have billed. Each has `isRetryable` and a plain message. Every error on an AI path (including `DecodingError`) is mapped to `AIError` before it reaches a log or a stored field, and only the case name and numeric codes are logged. Response bodies are never stored, logged, or shown.

### One state machine for every AI job

There are three jobs per entry: **text** (voice transcription or page transcription), **title**, and **insights**. Each follows the same persisted rules, so a force-quit, a relaunch, or a failure never loses track of a job and never repeats a paid request without limit. Failure state lives on `Entry` (and on each page for page transcription), not only in memory.

Per job, `Entry` stores: a pending flag (`awaitingText` for text, `titlePending`, `insightsPending`), an attempt count, and the last failure as a raw `AIError`/`TranscriptionError` case name.

- **Runs automatically** only when the job is pending, its prerequisites hold (below), the entry is not open in an editor or the page order screen (titles and insights only; transcription runs while open), the last failure is nil or retryable, and attempts are below the cap (text 3, title 2, insights 2).
- **Attempt counted before the request.** The count is incremented and saved before the `await`, so a crash mid-request still counts.
- **Page transcription counts progress, not passes.** A pass over a photo entry's remaining pages counts against the text cap only if it saved no new page, so backgrounding during a long 20-page run doesn't burn the cap while pages keep finishing. Spend stays bounded by a second cap on total page requests per entry (page count + 3), and a finished page is never re-sent.
- **Offline doesn't count and doesn't loop.** An `AIError.offline` failure rolls the attempt back, because no request reached the server. The coordinator marks itself offline for the session and stops sending until `NetworkMonitor` (an `NWPathMonitor` wrapper) reports the path satisfied again, then re-runs every queue once. Launch and returning to the foreground also re-run them. `ai.offline` is logged once per offline period, not per try.
- **Success** clears the flag, the count, and the failure.
- **Retryable failure** (network, rate limit, 5xx, Foundation Models not ready) keeps the flag and records the failure. Within a session it isn't retried again automatically; the next launch or return to the foreground tries again until the cap.
- **Non-retryable failure or cap reached** keeps the failure and stops automatic runs. For titles and insights the pending flag is cleared. For text, `awaitingText` stays but nothing automatic runs it again.
- **Retry / Run AI** (manual) resets the count and failure, sets the flag, and runs immediately. It is disabled while that job is already running for that entry.

**Old entries never go to the cloud on their own.** `SettingsStore.aiEnabledAt` is set each time AI is switched on. A voice recording goes to the cloud automatically only if the entry was created at or after `aiEnabledAt`; older stuck recordings keep using Apple automatically, and go to the cloud only when the user taps Retry. Photo entries need an explicit tap to be sent at all: "Transcribe N pages" on the order screen when AI is usable, or "Transcribe pages" in the editor for pages saved while AI was off, so turning AI on never sends saved pages by itself. `SettingsStore.automationStartedAt` is written once, the first launch of this build; entries created before it never get an automatic title or insights pass. Both rules use `createdAt`, never the user-editable entry date, so backdating an entry doesn't change what runs.

### Triggers

**One automatic AI pass per entry.** `Entry.automaticAIPassUsed` records it. An entry is eligible when it was created after `automationStartedAt`, has non-empty text, is not awaiting text, is not awaiting review, and, for photo entries, has `pagesConfirmed`. The pass happens at the first of these moments for an eligible entry:
1. the editor closes on it (including a voice entry the user typed into, and a photo entry whose text the user typed instead of transcribing, which never goes through review),
2. voice transcription succeeds while no editor has the entry open,
3. the user approves a photo entry's transcription,
4. the launch sweep finds it (covers entries whose editor never closed because the app was killed).

An unapproved photo entry is never eligible, so closing its editor or the launch sweep can't skip review. This eligibility rule lives in `AIPassTrigger` from Phase 6, before photo entries exist, so it never needs revisiting.

**Results are dropped if the entry changed underneath them.** `Entry.contentRevision` is an integer bumped by every page change and by a restart. Page, title, and insights jobs capture it with the request and, after the `await`, re-fetch the entry and drop the result if the revision moved (and, for a page, if that page no longer exists at the same index, or the entry is no longer `pagesConfirmed && awaitingText`). This stops an in-flight request from writing old text, a title, or insights into a restarted entry, or writing to a deleted page.

At that moment, in one save: `automaticAIPassUsed = true`; `titlePending = true` if the title generator is usable and the title isn't user-typed; `insightsPending = true` if AI is on, insights are automatic, and there is a text account with a key. The pass is used even when nothing was enabled or no key was set: turning AI on or adding a key later never analyzes entries that already had their moment. Run AI covers those entries.

**Open entries are left alone.** `EditorPresence` (an `@Observable` set of open entry IDs in the environment) is updated in the editor's `onAppear`/`onDisappear`. Title and insights jobs for an open entry wait, and read the entry's text at request time.

**Launch work runs in parallel lanes.** `RootView.task` starts ingest then transcription (voice and pages) in one task, and titles plus insights in another. Each coordinator also re-runs its queue when a job is flagged and when the scene becomes active.

### Speech

**The voice queue only sees voice entries.** Today `TranscriptionCoordinator` fetches every `awaitingText` entry (`TranscriptionCoordinator.swift:49`) and silently skips ones without audio (`:63`). Once attempts are persisted, a photo entry in that queue could be counted or failed. The fetch is filtered to `sourceRaw == "voice"`, photo entries go only to `PageTranscriptionCoordinator`, and the "Getting text" badge (`EntryListView.swift:97`) and "Text from your recording" placeholder (`EntryEditorView.swift:43`) get photo wording ("Transcribing pages", "Text from your pages will appear here").

**Speech engine is resolved per call.** `TranscriptionCoordinator` asks a `TranscriberRouter` for a transcriber for each voice entry. Cloud is chosen when AI is on, `speechEngine == cloud`, the speech account has a key, and the entry is eligible (created after `aiEnabledAt`, or a manual Retry). Otherwise Apple.

**Fallback to Apple, recorded on the entry.** If the cloud call fails and "Use on-device when cloud fails" is on (default on), the same entry is transcribed with Apple in the same pass. If Apple succeeds, the cloud failure doesn't count against the text job; `Entry.textFallbackReasonRaw` records why, and the editor shows "Transcribed on device: couldn't reach OpenAI" until the user dismisses it or edits. If Apple also fails, the Apple error is recorded as the job's failure. `Entry.textGeneratedBy` records which engine and model produced the text.

**Cloud audio is always m4a.** Any non-m4a audio (unconverted CAF) is converted before upload.

**Long recordings are split at quiet points.** When a recording exceeds the chunk target (20 minutes for OpenAI, or 90% of the byte limit), `AudioChunker` cuts at the quietest 50 ms window within 15 s of each boundary, exports each segment as m4a with `AVAssetExportSession` passthrough, and transcribes them in order with the previous chunk's tail as the prompt. Target and search window are injected for tests. A chunk failure fails the entry and counts one attempt; an hour-long recording is uploaded at most three times automatically.

**A cloud request in flight when the app backgrounds** is wrapped in `beginBackgroundTask`. If iOS still suspends it, the failure is retryable and counts toward the cap.

### Photo entries

**Capture and import.** The list toolbar gains a third new-entry button, "Photograph pages" (identifier `newPhotoEntryButton`; the existing `newEntryButton` and voice button are unchanged, so UI tests keep working). It is hidden when `VNDocumentCameraViewController.isSupported` is false (the simulator). It opens the VisionKit document camera, which captures pages in order with crop and perspective correction. The page order screen also offers "Add from Photos" (`PhotosPicker` with `selectionBehavior: .ordered` and `maxSelectionCount` set to the remaining room, loaded as `Data`) and "Scan more pages", so camera and library pages can be mixed. Library images are used as they are (no automatic crop or straightening). Up to 20 pages per entry: a scan or import that would pass 20 keeps the first pages that fit and says how many were left out. Picker items that fail to load (for example iCloud originals that can't download) are skipped with a count shown; the rest are added.

**Pages are saved as soon as they reach the app.** The document camera only hands pages back when the user taps Save in the camera (`documentCameraViewController(_:didFinishWith:)`), so a force-quit inside the camera loses that scan; everything after that point is kept. On the first pages delivered, the entry is created with `source = .photo` and `pagesConfirmed = false`, and each page is saved immediately. A force-quit on the order screen leaves an entry the list shows as "Pages not confirmed"; tapping it reopens the order screen instead of the editor. `isBlank` counts pages, so an entry with pages is never auto-deleted.

**The order screen is its own full-screen cover.** `PageOrderView` is presented with `fullScreenCover` from the list (new and unconfirmed entries) and from the editor ("Edit pages"). A cover over the editor doesn't fire the editor's `onDisappear`, so `close()` never runs underneath it. `PageOrderView` registers the entry with `EditorPresence` itself, so title and insights jobs wait while it is open. Nothing is deleted on `onDisappear` (presenting the camera or picker fires it); an unconfirmed entry with no pages is deleted only by the explicit Cancel or Done action.

**Images are stored for reading, sent for transcription, and never decoded at full size for display.** `PageImageProcessor` works one page at a time off the main thread, releasing each image before the next: it normalizes orientation (HEIC and EXIF from the library, the camera's own output), stores a JPEG with the long edge capped at 2400 px (quality 0.8; expect roughly 1 to 2.5 MB for dense handwriting, measured on a real journal in the smoke test), stores a ~400 px thumbnail inline on `EntryPage` for grids and strips, and builds the upload copy at a long edge of 2048 px (checked against the model's high-detail downscaling in the Phase 3 live test and reduced if the model scales it down anyway). Full-size images are only decoded in the zoomable single-page view, through `CGImageSourceCreateThumbnailAtIndex` with `kCGImageSourceCreateThumbnailWithTransform`. Pages are kept for the life of the entry; the photo is the original journal.

**Confirming the order locks it.** The order screen shows page thumbnails with drag to reorder, delete (which deletes the `EntryPage` model, not just the link, so no orphaned image stays behind), add more, and a confirm button. With AI usable, the button reads "Transcribe N pages" and sets `pagesConfirmed = true` and `awaitingText = true`. With AI off or no key, it reads "Save pages" and sets only `pagesConfirmed`; the editor then shows the pages with "Turn on AI in Settings to transcribe these pages, or type the text yourself," and a "Transcribe pages" button once AI is usable. Typing into a confirmed photo entry works like any entry and needs no review, since the user wrote it.

**One request per page, in order.** The page coordinator transcribes pages from first to last, one request each. The request sends the page image, the last ~300 characters of the previous page's text for continuity, and asks for structured output `{text, writtenDate}`: the text transcribed verbatim (the writer's wording and spelling, line breaks as paragraphs, `[illegible]` for words that can't be read, nothing added or corrected) and the date written on the page if one is fully legible (year, month, day), else null. Each page's result is saved on its `EntryPage` as it arrives: `transcribedText == nil` means not done yet, and `""` means a done page with no text (a blank page), so a blank page is never re-sent. A failure on page 3 re-sends only pages 3 onward. When the last page is done, the page texts are joined with blank lines and handed to `applyGeneratedText`. Only if it applies (the user didn't type meanwhile) do `textGeneratedBy` and `textReviewPending = true` get set.

**Typing during transcription keeps the page text available.** If the user typed while pages were being transcribed, `applyGeneratedText` refuses, `awaitingText` is already cleared by `userDidEditText`, and the entry is treated as typed (no review, pass on editor close). The pages keep their transcriptions, and the editor offers "Replace with page transcription" whenever every page has text; it asks first, then sets the joined text and `textReviewPending = true`, so the paid output of a long run isn't lost to one stray keystroke.

**Review, correct, approve.** A photo entry with `textReviewPending` opens in the editor with page thumbnails in a swipeable strip above the text (tap for a zoomable full page) and a banner: "Check the text against your pages, then approve it." Editing the text doesn't approve it. "Approve text" clears `textReviewPending` and is trigger 3 for the automatic pass. Run AI is unavailable on an unapproved photo entry. A date read from a page appears as a suggestion (see Entry dates).

**Changing pages after transcription starts restarts the entry, but only when the pages actually change.** Once `pagesConfirmed` is true, "Edit pages" opens `PageOrderView` in edit mode, working on a draft: an ordered list of existing page IDs plus pending additions and removals. Nothing on the entry changes while the user edits the draft, and Cancel discards it. The confirm button compares the draft to the saved pages. If they're the same, it just closes. If they differ, it shows "Changing pages will erase this entry's text, title, and insights and transcribe the pages again," and on confirmation `restartPages(applying: draft)` runs in one save:
- applies the draft (new pages added, removed pages deleted, indexes rewritten contiguously),
- bumps `contentRevision` (so any in-flight page, title, or insights request drops its result),
- clears `text`, `title`, `titleWasGenerated`, `textWasGenerated`, `textEditedByUser`, `originalText`, `textGeneratedBy`, `textFallbackReasonRaw`, `textReviewPending`, `suggestedEntryDate`, and every page's `transcribedText` and `writtenDate`,
- clears `awaitingText`, `titlePending`, `insightsPending`, every attempt count and failure, and `automaticAIPassUsed`,
- deletes the entry's insights,
- sets `pagesConfirmed` and `awaitingText` again when AI is usable (the confirm tap is the user's go-ahead), otherwise only `pagesConfirmed`.

The pages that remain, `createdAt`, and the entry date are kept. Because the user started it, the restarted entry gets a fresh automatic pass after re-approval.

**Diagnostics never include images or page text.** Events carry page counts, indexes, byte sizes, pixel dimensions, origins (camera or library), durations, and token counts.

### Titles

**Typed, generated, or derived.** `Entry.title` (default `""`) and `titleWasGenerated`. `applyGeneratedTitle(_:)` writes only when the title is empty or still generated; typing in the title field clears `titleWasGenerated`, and clearing the field hands it back to generation. Setting `titleGenerator`: `off`, `onDevice`, `openAI`. Its default is `onDevice` when Foundation Models is available on first read, otherwise `off`; the default is computed, not written back. When `title` is empty, `Entry.displayTitle` derives one from the text: the first line, cut at a word boundary to about 60 characters, or "Untitled" for an entry with no text. The list shows `displayTitle` as the headline and hides the text preview when it would repeat the headline; the editor's title field shows `displayTitle` as a placeholder. Title generation is its own small request, separate from insights. On-device titles work with AI off; the trigger doesn't depend on `aiEnabled` or `insightsTrigger`.

**A title alone keeps an entry.** `isBlank` becomes `title.isEmpty && text.isEmpty && audioData == nil && pages.isEmpty`, and typing into the title of a new entry creates the entry the same way the first keystroke in the text does.

### Insights

**A separate model.** `EntryInsights` holds AI output for one entry, linked by an optional relationship with cascade delete from `Entry`. Run AI replaces its fields in place. `EntryInsights.isCurrent(for:)` compares the entry's text hash with `sourceTextHash` and `appliedTextHash`; when neither matches, the view shows "Entry changed since these insights" and offers Run AI.

**One structured call per insights run, one field per enabled section.** The schema is built at runtime from the enabled sections: `summary`, `moods`, `themes`, `tags`, `mentions`, `openThreads`, `cleanedText` (voice entries only), `writtenDate` (typed entries only), and one field per enabled custom prompt. Every field is nullable. Custom prompt fields are keyed from the prompt's UUID (`custom_` plus its first 8 hex characters) with a key-to-prompt map per request. The system prompt follows build plan §4.1: observe and organize, don't restate the entry, no advice or therapy language. The prompt includes the user's 50 most used existing tags. `cleanedText` is left out when the entry is longer than 12,000 characters, and the view says why. After the `await` the coordinator re-fetches the entry. If the entry is gone the result is dropped. If its text changed since the request was built, the insights are still stored (stale by hash) but cleanup is never applied and no date is suggested.

**Moods, themes, tags, and mentions are different things.**
- *Moods*: one primary mood and up to two secondary moods from the closed vocabulary below, or none. `#Predicate` can filter `primaryMoodRaw` directly; secondary moods and tags are `[String]` and are filtered in memory, which is fine at journal scale.
- *Themes*: two to four short phrases on what the entry is about. Free text, entry-specific.
- *Tags*: up to eight short lowercase labels for filtering and grouping across entries. Free text, steered toward the user's existing tags.
- *Mentions*: named things in the entry, each `{name, kind}` with `kind` one of `person`, `place`, `organization`, `project`, `event`, `other`. Raw per-entry extractions, not resolved entities. Build plan Phase 2 (entity resolution, the knowledge graph, `NLTagger` as a free first pass) builds on them.

**Cleaned-up text, voice entries only, keeps the original on the entry.** Cleanup fixes punctuation, paragraphs, and obvious transcription errors without changing wording or meaning. It is requested only for voice entries. The result is stored in `EntryInsights.cleanedText`. Applying it goes through `Entry+Editing.applyCleanedText(_:)`, which copies the current text to `Entry.originalText` if that is still `nil`, then sets `text` and records `appliedTextHash`. The original lives on `Entry`, so regenerating insights can never lose it, and only the first pre-cleanup text is kept.
- *Applying requires the text to be exactly what was analyzed* (hash equals `sourceTextHash`), for the manual tap and automatic application alike. Otherwise "Use this text" is disabled with "Your entry changed since this was generated. Run AI to clean up the current text."
- *Automatic application* (`autoApplyCleanedText`, default off) happens when the insights run completes, the text still matches, and no editor has the entry open. If the entry is open, the cleanup stays a suggestion.
- *Revert to original* restores `originalText` and clears it. If the text changed since the cleanup was applied, it asks first.

**Insights open as a sheet.** `EntryEditorView.onDisappear` runs `close()`, which deletes blank entries and may discard audio. A sheet over the editor does not fire it.

### Entry dates

**Two dates with different jobs.** `createdAt` stays the system record of when the entry entered the app and never changes; automation rules use it. The entry date is when the entry belongs in the journal; it drives the list order, the editor's date, and everything later built on time (mood trends, rolling summaries, the graph's timeline).

**Full timestamp by default, noon of the chosen day when the user changes it.** One date plus a display flag, both set only through `Entry+Editing`:
- `entryDate: Date` equals `createdAt` (date and time) until the user changes it. For recordings that is the recording file's creation time, as `createdAt` already uses.
- Picking a day sets `entryDate` to noon of that day in the current time zone and `entryDateIsDayOnly = true`. The flag exists so the app shows "Mar 3, 2025" instead of a made-up "12:00 PM".
- Display: flag off shows date and time; flag on shows the date only.
- "Use original date" resets `entryDate` to `createdAt` and clears the flag.
- A backdated entry sorts at noon among that day's timed entries, which is fine for a journal list.
- Known limit, accepted: noon keeps the shown day correct for any time zone change under 12 hours; viewing a backdated entry 12 or more hours away can show the neighboring day.

**Existing entries are repaired at launch, not in a migration stage.** The automatic lightweight migration gives every existing entry the same default `entryDate`. Rather than a custom migration stage (which needs exact copies of the old model and runs only once, so a failed save would leave wrong dates for good), `EntryDateRepair` runs at every launch before the list appears and enforces an invariant the design already guarantees: when `entryDateIsDayOnly` is false, `entryDate` equals `createdAt`. Any entry that breaks it is fixed and saved. It is idempotent, cheap at journal scale (one fetch of entries with the flag off, compare, usually zero writes), and also catches any later bug that breaks the invariant.

**Sorting and display.** The list sorts by `entryDate` descending, then `createdAt` descending, so the many backdated entries that share noon of the same day keep a stable order. When `entryDateIsDayOnly` is on, the row and editor also show a small "Added Sep 15, 2026". The editor's date becomes a button that opens a date-only picker with "Use original date".

**Suggested dates.** `Entry.suggestedEntryDate` holds a day found by AI (stored as noon of that day): from the first page with a legible `writtenDate` (photo entries), or from the insights `writtenDate` field (typed entries, for pasted text that states its own date). The prompt asks only for the date the entry itself was written on, ignoring other dates mentioned in it, and only when year, month, and day are all present. The model returns `"yyyy-MM-dd"`, parsed into noon of that day; a partial or invalid date is dropped. A suggestion is stored only when its day differs from the local day of `entryDate`. Accepting it sets the date like a manual change. Any date change clears a suggestion for the same day, and the banner is only shown while the suggestion's day still differs from the entry's day. The editor shows "Written on March 3, 2025? Use this date" with Use and Dismiss; both clear the suggestion. A suggestion never changes the date by itself.

### Persistence

**One schema change, lightweight, tested against a real old store.** All new `Entry` fields, `EntryPage`, and `EntryInsights` land in a single phase. Every new attribute has a default or is optional and the new relationships are optional, so SwiftData's automatic lightweight migration handles it with no `VersionedSchema`. (Revision 3 planned a versioned schema with a custom stage; the revision 4 review showed the old model copy has to match today's `Entry` exactly or the existing store fails to open, and the stage's one-shot backfill is less safe than the launch repair above. Versioned schemas get introduced when a change first needs a real migration.) Proof comes from a fixture instead of a hand-copied old model: before any model change, a store is written by today's app (`main`) with typed, voice (with audio), and awaiting-text entries across several days, and committed as `MindloreTests/Fixtures/v1-store.bundle` (an opaque bundle so the hidden external-storage folder is copied into the test bundle intact; the simulator can't read the fixture from the source tree under `~/Documents`). The migration test copies it to a temp directory, opens it with the new schema, runs `EntryDateRepair`, and checks every entry and field survived with `entryDate == createdAt`. A device smoke step installs over the current build with real entries before any later phase lands.

**`updatedAt` follows content, not insights.** Transcribed text, a generated title, applied cleanup, a changed entry date, and page changes move `updatedAt`. Writing insights does not; the stamping helper skips entries whose only change is the `insights` relationship.

## Mood vocabulary

Locked 2026-09-15 (owner asked Claude to write it). Eight categories, 43 moods. Changing a mood after insights exist means re-running AI on those entries, so additions are cheap and renames or removals are not.

How it works:
- Each category has a fixed `valence` (-1, 0, +1) and `energy` (low, medium, high), so trend charts can plot categories without per-mood tuning.
- An entry gets one primary mood and up to two secondary moods, or no mood at all when the text carries no emotional content (a shopping list, logistics). The model is told to leave moods empty rather than guess.
- Raw values are the camelCase names below (`burnedOut`). The category is derived from the mood, never stored.
- Descriptions go into the schema so the model picks consistently, and into the insights view so the user sees what a mood means.

| Category | Valence / energy | Moods |

| **Joyful** | +1 / high | **joyful**: happy, light, glad · **excited**: eager, looking forward to something · **energized**: motivated, ready to act · **proud**: satisfied with something done · **confident**: sure of yourself or a decision · **inspired**: struck by an idea or possibility |
| **Calm** | +1 / low | **content**: things feel fine as they are · **calm**: settled, unhurried · **grateful**: thankful for someone or something · **relieved**: a worry has lifted · **hopeful**: expecting things to get better |
| **Connected** | +1 / medium | **loved**: cared for by someone · **connected**: close to the people around you · **supported**: someone has your back · **compassionate**: feeling for someone else |
| **Reflective** | 0 / medium | **reflective**: thinking things over · **curious**: wanting to understand something · **nostalgic**: drawn back to the past · **uncertain**: unsure what to think or do · **conflicted**: pulled in two directions |
| **Anxious** | -1 / high | **anxious**: worried about what might happen · **stressed**: under pressure · **overwhelmed**: too much at once · **restless**: unable to settle · **afraid**: scared or threatened · **insecure**: doubting yourself or your place |
| **Angry** | -1 / high | **frustrated**: blocked or thwarted · **irritated**: annoyed by small things · **angry**: strongly upset at someone or something · **resentful**: holding onto a grievance · **jealous**: wanting what someone else has |
| **Low** | -1 / low | **sad**: down, sorrowful · **lonely**: missing connection · **disappointed**: let down by someone or something · **hurt**: emotionally wounded · **guilty**: regret over something you did · **ashamed**: feeling bad about who you are · **hopeless**: unable to see things improving |

## Test plan

Unit tests carry the weight: every HTTP request shape against fixtures, every error mapping, `AIJobPolicy` exhaustively, the four coordinators with fakes and relaunch simulated by a new coordinator over the same file store, the pass trigger, page ordering and restart, schema and prompt building, migration from the committed old-store fixture plus `EntryDateRepair`, restart and revision races, noon-of-day dates across time zones, chunk boundaries on generated audio, image processing on fixtures, Keychain against the simulator keychain with a test service name. No test hits the network. `OpenAILiveTests` runs only when `MINDLORE_OPENAI_KEY` is set in the scheme environment. The document camera can't run in the simulator; UI tests use `-uiTestingFakePages`, and real capture is covered by the device smoke test.

## Risks and open questions

- **PR size.** Photo entries and dates roughly double the work. The phases are ordered so photos (Phases 7 and 8) can split into a stacked PR if review gets unwieldy.
- **Handwriting accuracy.** Depends on handwriting, lighting, and model. Review before insights contains the damage; the page model is a setting so a stronger model can be chosen. Cost per page is a few cents at high detail; confirm with the live test and a real journal.
- **Library imports aren't straightened.** Photos taken outside the document camera may be skewed or include the desk. The vision model usually copes; automatic crop for imports is out of scope.
- **Storage.** Pages are kept forever at roughly 1 to 2.5 MB each for dense handwriting (measured in the smoke test); a year of daily three-page entries is about 1 to 3 GB. Acceptable for a prototype; revisit before sync.
- **Written dates without a year** ("March 3") aren't suggested. Many journals omit the year; a later version could infer it from nearby entries.
- **Mood vocabulary is locked** once Phase 9 stores the first insight.
- **Default models.** `gpt-transcribe`, `gpt-5.6-terra` for pages, `gpt-5.6-luna` for text, per current docs; `OpenAILiveTests` confirms them in Phase 3.
- **OpenAI's undocumented ~1400 s duration cap.** Chunking at 20 minutes leaves margin.
- **SwiftData migration.** Automatic lightweight migration plus `EntryDateRepair`. The committed old-store fixture test and the Phase 1 device check gate everything after. If the fixture fails to open, fall back to a `VersionedSchema` with an exact copy of today's `Entry`.
- **Camera scans aren't saved until the user taps Save in the document camera.** A force-quit inside the camera loses that scan. VisionKit gives no per-page callback.
- **Cost bounds.** Automatic spend per entry is capped: text 3 attempts, title 2, insights 2, one automatic pass; offline attempts don't count. No cost UI in this PR; token counts are logged.
- **Backgrounding mid-upload.** `beginBackgroundTask` buys about 30 s; a suspended upload fails, counts an attempt, and retries next launch.
- **Foundation Models availability.** Many phones can't run it. The default falls back to no AI titles.
- **Mentions are unresolved.** Resolution is build plan Phase 2 work.
- **Privacy review pending.** Copy is neutral after Phase 0 (and the new camera string is neutral), but `PrivacyInfo.xcprivacy` declarations and any in-app disclosure need the separate review before an external build.

## Not in scope

- Providers other than OpenAI in the UI; the protocols are ready for them
- Custom base URLs in the UI, local network permissions and ATS exceptions
- Privacy cards, disclosure sheets, privacy claims
- On-device OCR for pages, automatic crop or straightening of imported photos, PDF import
- Editing or re-transcribing a single page after transcription starts (any page change restarts the entry)
- Apple Foundation Models for anything other than titles
- Entity resolution, `NLTagger` extraction, embeddings, rolling summaries, the knowledge graph (tags and mentions are stored for it)
- Bulk Run AI across many entries; bulk import of past journals
- Re-transcribing a voice entry that already has text with a different engine
- Streaming responses, live captions
- Background `URLSession` uploads, per-chunk resume
- Cost tracking UI, token budget setting
- Time of day on backdated entries; inferring a missing year on written dates
- Per-entry prompt overrides or a spoken-question feature
